# Продвинуто 1. Координация нескольких твиков

Один целевой класс/метод — ваш твик + ещё 2–3 чужих. Что происходит, как не победить соседа, и как сделать так, чтобы ваш твик уживался с экосистемой.

## 1. Что происходит, когда два твика хукают одно и то же

Хук — это замена `IMP` в таблице методов. Два хука на один метод превращаются в **цепочку**:

```
original IMP ← twikB_hook ← twikA_hook ← (current IMP)
```

Порядок — в котором TweakLoader загрузил dylib'ы. Он **не детерминирован**: алфавитный порядок, mtime файлов, etc.

При вызове:

1. Приложение вызывает `-method` → попадает в `tweakA_hook`.
2. `tweakA_hook` делает `%orig(...)` → попадает в `tweakB_hook`.
3. `tweakB_hook` делает `%orig(...)` → попадает в оригинал.
4. Оригинал выполняется, возвращает значение.
5. `tweakB_hook` получает значение, может модифицировать.
6. `tweakA_hook` получает значение, может модифицировать.
7. Приложение получает финальное значение.

Если каждый твик корректно зовёт `%orig(...)` — всё работает. Если один из них решает **не** звать `%orig` — цепочка обрывается, и твики ниже не выполнятся.

## 2. Правила «хорошего соседа»

1. **Всегда вызывайте `%orig`** (с подходящими аргументами). Исключение — осознанное замещение (глава V.3), которое документируется в README твика.
2. **Не меняйте тип возврата** (nil вместо не-nil и наоборот — ломает контракт для нижних твиков).
3. **Используйте уникальные associated keys** (`static char kMyUniqueName`); если ваш ключ совпадёт с чужим — вы перезапишете его данные.
4. **Prefix ваших новых методов** через `%new` — `-com_example_mytweak_showToast:` вместо `-showToast:`, чтобы не конфликтовать с другим твиком, который добавил `-showToast:` с другой семантикой.

## 3. Детекция конфликтов

Простой способ — логировать имя класса и адрес IMP:

```objc
%ctor {
    gLog = os_log_create("com.example.mytweak", "diag");

    Class cls = [UIViewController class];
    SEL sel = @selector(viewDidLoad);
    Method m = class_getInstanceMethod(cls, sel);
    IMP currentIMP = method_getImplementation(m);
    os_log(gLog, "pre-hook IMP of viewDidLoad = %p", currentIMP);
}
```

Если `pre-hook IMP` отличается от оригинала (из `dlsym` или static dump) — значит, кто-то уже хукнул этот метод.

Расширенно — через `otool`:

```bash
otool -ov /path/to/UIKit | grep -A2 "viewDidLoad"
# покажет оригинальный offset
```

Сравнение с рантаймом в вашем %ctor даёт picture.

## 4. Load order через Logos `%group`

Logos даёт возможность условно инициализировать хуки:

```objc
%group CoreHooks
%hook UIViewController
- (void)viewDidLoad { %orig; /* ... */ }
%end
%end

%group OptionalHooks
%hook UIViewController
- (void)viewDidAppear:(BOOL)animated { %orig(animated); /* ... */ }
%end
%end

%ctor {
    // Core — всегда:
    %init(CoreHooks);

    // Optional — если нет конфликта с конкретным tweak'ом:
    if (!NSClassFromString(@"SomeOtherTweakMarker")) {
        %init(OptionalHooks);
    }
}
```

`SomeOtherTweakMarker` — договорённость сообщества: конфликтующие твики могут экспортировать специальный класс-маркер. Если он присутствует — ваш твик вежливо отступает.

## 5. Darwin notifications для координации

Два твика могут обмениваться состоянием через Darwin notifications (глава IV.8). Пример:

- Твик A управляет глобальным флагом «dark mode active».
- Твик B хочет подстроиться под этот флаг.

Твик A постит `notify_post("com.community.darkmode.changed")`. Твик B подписывается через `notify_register_dispatch(...)`.

Это неформальный «протокол» — работает, если оба согласились на имя notification'а.

## 6. Разделяемые preference domains

Для твиков, которые хотят читать общие настройки:

```objc
// Твик A пишет:
CFPreferencesSetAppValue(CFSTR("darkMode"), kCFBooleanTrue,
                          CFSTR("com.community.theme"));

// Твик B читает:
Boolean exists;
Boolean darkMode = CFPreferencesGetAppBooleanValue(
    CFSTR("darkMode"), CFSTR("com.community.theme"), &exists);
```

Разделяемый domain (`com.community.theme`) — договорённость. Если несколько твиков используют его, они делят настройки.

## 7. «Не хукать `objc_msgSend`»

Отдельный пункт: **никогда** не хукайте `objc_msgSend`. Это:

- Горячая точка Objective-C runtime (сотни тысяч вызовов в секунду).
- Любая логика в хуке → замедление приложения.
- Любая ошибка → крах всей системы ObjC.

Если нужна «универсальная» точка перехвата метода — используйте `method_setImplementation` на конкретном методе, не `objc_msgSend`.

## 8. Таблица «что я могу испортить соседу»

| Ваше действие | Что ломает у соседей |
|---|---|
| Не зовёте `%orig` | Их хук этого метода не выполнится |
| Возвращаете `nil` вместо non-nil | Их хук, зависящий от значения, упадёт |
| Используете общий associated key | Перезаписываете их данные |
| Удаляете subview, который они добавили | Их UI падает |
| Хукаете `+load` | Непредсказуемый порядок |
| Хукаете `objc_msgSend` | Всё ломается |
| Инжектируете во все процессы (`Classes = NSObject`) | Их filter plist на конкретное приложение потерял смысл |

## 9. Хорошая практика: README твика

Публикуя твик — документируйте:

- Какие классы и методы вы хукаете.
- Какие associated keys используете (с prefix'ом).
- Какие Darwin notifications постите/подписываетесь.
- Какие preference domains читаете/пишете.
- Какие potentials conflicts.

Это помогает другим авторам обходить ваш твик стороной или интегрироваться.

## 10. Debug workflow для конфликтов

Пользователь жалуется «ваш твик не работает с X-tweak»:

1. Попросить пользователя установить только ваш — работает?
2. Попросить установить только X — работает?
3. Оба — сломано.
4. Поставить вариант с диагностическим логом `pre-hook IMP = %p` — узнать, кто хукает первым.
5. Попросить X-tweak-maintainer зайти на договорённость (prefix, notification, protocol).

## 11. Что подтверждено

- **Подтверждено Apple docs**: `method_getImplementation`, `method_setImplementation`.
- **Подтверждено практикой**: load order TweakLoader не детерминирован.
- **Подтверждено**: `objc_msgSend` в hot path — анти-паттерн.
- **Требует проверки**: конкретные протоколы координации — не формализованы, зависят от конкретных community-tweaks.

## 12. Выводы

Главный тезис: **твик живёт в экосистеме**. Другие твики могут хукать те же методы; будьте вежливым соседом — зовите `%orig`, используйте уникальные keys, документируйте.
